1. AI, ML and deep learning

Think of three circles, one inside another.

Term Meaning Example
Artificial intelligence (AI) any technique that makes a computer act intelligently, including hand-written rules a chess program, a route planner
Machine learning (ML) a part of AI where the computer learns rules from examples instead of being told them predicting which customers will leave
Deep learning (DL) a part of ML that uses neural networks with many layers face recognition, speech-to-text, ChatGPT

Traditional programming: data + rules you write → answers. Machine learning: data + past answers → rules the computer finds.

Why use ML? When the rules are too many, too subtle, or keep changing. When not to: when a simple, stable rule already works (tax brackets), or when there are no past examples with answers to learn from.

For data in tables (customer records, transactions, measurements), classic ML (linear models, trees, forests, boosting) is still usually the best tool. Deep learning dominates images, audio and text.

2. The ML workflow

Every project follows the same eight steps:

  1. Frame the problem (what do we predict, for what decision?)
  2. Get and inspect the data
  3. Split: lock away a test set
  4. Preprocess: fill gaps, scale numbers, encode categories
  5. Baseline: the score of "no intelligence"
  6. Train and compare models
  7. Evaluate once on the test set
  8. Deploy and monitor

Notice the order: we split (step 3) before preprocessing (step 4). This one habit prevents a whole family of mistakes (section 7).

3. Framing a problem

A business wish ("we lose too many customers") is not a prediction task. Make it precise:

Part Churn example
Prediction question Which current customers will cancel next month?
Target (y) Churn = Yes / No
Features (X) contract, tenure, monthly bill, services, payment method…
One row = one customer
Decision the retention team calls the riskiest customers first
Metric (Session 2) e.g. how many real leavers we catch

Template (your first deliverable):

We want to predict [target] for [each row] using [features available at prediction time], so that [who] can [decision]. We measure success with [metric] and must beat [baseline].

The words available at prediction time matter: if you would not know a column's value on the day you make the prediction, it cannot be a feature.

Task types

Task Target Example
Regression a number medical charges, house price
Classification a category (often yes/no) churn, income > $50K, survived
Clustering none customer segments
Anomaly detection none (mostly) strange transactions

4. Supervised vs unsupervised

  • Supervised: every training row has the answer (label). The model learns to predict it for new rows. Like studying with an answer key. Regression and classification are supervised.
  • Unsupervised: no answers. The model looks for structure: groups, unusual rows, simpler summaries. Like sorting photos into piles without being told the categories.

Labels are often the expensive part: someone must wait to see who churned, or pay an expert to label each example.

5. Tabular data: features and target

One row = one example; one column = one property.

  • ID columns (e.g. customerID) are name tags. Drop them; a model could memorise them.
  • X (features): the input columns, numeric or categorical.
  • y (target): the column to predict.
X = df.drop(columns=["customerID", "Churn"])
y = (df["Churn"] == "Yes").astype(int)     # 1 = left, 0 = stayed

Always check the target balance first

Only 26.5% of customers left. A model that always says "stays" is right 73.5% of the time and is completely useless (it finds no leavers). Know this number before you trust any accuracy.

6. Train, validation and test

Why split? A student who saw the exam paper the night before scores 100% but has learned nothing. Testing a model on rows it trained on is the same cheat.

Set Job
Train (~60–80%) the model learns from it
Validation (or cross-validation) we choose between models and settings
Test (~20%) a locked box, opened once at the end for the honest final score

If you look at the test score, change something, and look again, your test set has become a validation set, and your final score is optimistic.

One split is luck

The same model on the same data scored anywhere from 78.8% to 81.8%, depending only on which customers landed in the test set. So: fix random_state (repeatable results), and use cross-validation for decisions (Session 2).

How to split

Method Use when
Random regression with independent rows
Stratified (stratify=y) classification: keeps the same class balance in train and test
Time-based data with dates: train on the past, test on the most recent period
Group-based several rows per person: keep each person on one side 
X_train, X_test, y_train, y_test = train_test_split(
    X, y, test_size=0.2, stratify=y, random_state=42)

7. Data leakage

Leakage = the model gets information during training that it will not have when used for real. The score looks great; the model fails in production.

  • Left: a column recorded after customers cancel ("days since last payment"; simulated for teaching) pushes accuracy from 80.5% to 93.4%. On the day we predict, nobody has cancelled yet, so the column doesn't exist.
  • Right: duplicated rows end up on both sides of the split; the tree "recognises" test customers it memorised (72.8% → 82.9%).

The five leaks to hunt for

Leak Example Prevention
Target leakage a column created after the outcome ("refund issued", "cancellation reason") Is it known at prediction time?
Preprocessing before split a scaler/imputer fitted on all rows split first; use a pipeline
Duplicates the same record in train and test df.duplicated().sum() before splitting
Time travel using the future to predict the past time-based split
Group leakage one patient's scans in train and test group-based split

Red flag: a score that seems too good to be true usually is. Find out which column is doing the work.

8. Preprocessing

Numbers

  • Missing values: models can't calculate with blanks. Fill with the median (robust to outliers), but first ask why the value is missing. In the churn data, the 11 blank TotalCharges all belong to brand-new customers (tenure 0), so the true value is $0, not the average.
  • Scaling: put numbers on a similar scale with StandardScaler (subtract the mean, divide by the standard deviation). Needed for linear models, distance-based methods and neural networks. Trees don't need it.

Categories

Option Use
Label numbers (0, 1, 2…) ❌ for unordered categories: invents a false order
One-hot encoding ✅ default: one 0/1 column per category
Ordinal ✅ only when the order is real (small < medium < large)
Target / frequency encoding many categories (e.g. cities); leaks if done before splitting

Use OneHotEncoder(handle_unknown="ignore") so that a new category in production doesn't crash your system.

The golden rule

fit = learn something from data (mean, median, categories). Fit only on the training rows, then transform train, test and future rows with what was learned.

9. Baselines

A baseline is the simplest possible answer: always predict the most common class (classification), always predict the average (regression), or a one-line business rule.

Model Accuracy Precision Recall (leavers caught)
Always "stays" 73.5% — 0%
Rule: month-to-month → leaves 65.3% 42.6% 88.0%
Rule: month-to-month AND fiber → leaves 75.1% 52.7% 59.4%
Logistic regression (learned) 80.5% 65.7% 55.9%

Lessons: accuracy alone lies; a one-line rule can be very useful; and a model must earn its complexity against the best simple rule. If a rule is good enough for the business, ship the rule.

10. scikit-learn: estimators, transformers, pipelines

Object Methods Examples
Transformer fit(X) learns, transform(X) changes data SimpleImputer, StandardScaler, OneHotEncoder
Estimator (model) fit(X, y) learns, predict(X) answers DummyClassifier, LogisticRegression
Pipeline chains steps; behaves like one model impute → scale → encode → model

Why always use a pipeline? (1) No leakage: every step is fitted on training rows only, even inside cross-validation. (2) No mismatch: new rows get exactly the same treatment. (3) One object to save and deploy.

from sklearn.compose import ColumnTransformer
from sklearn.pipeline import make_pipeline
from sklearn.impute import SimpleImputer
from sklearn.preprocessing import StandardScaler, OneHotEncoder
from sklearn.dummy import DummyClassifier

pre = ColumnTransformer([
    ("num", make_pipeline(SimpleImputer(strategy="median"), StandardScaler()), numeric_cols),
    ("cat", make_pipeline(SimpleImputer(strategy="most_frequent"),
                          OneHotEncoder(handle_unknown="ignore")), categorical_cols),
])
baseline = make_pipeline(pre, DummyClassifier(strategy="most_frequent"))
baseline.fit(X_train, y_train)
print(baseline.score(X_test, y_test))      # accuracy = 0.7346

Self-check

1. A model scores 95% accuracy on a disease that 5% of patients have. Impressive?Not yet: "always healthy" also scores 95%. Compare with the baseline and check recall.
2. A column "refund_issued" predicts churn almost perfectly. Use it?No. Refunds happen after cancelling, so it is not known at prediction time: target leakage.
3. You fit a StandardScaler on all the data and then split. What's wrong?Test-set statistics influenced training (preprocessing before split). Split first and put the scaler in a pipeline.
4. You predict next month's sales from three years of daily data. Which split?Time-based: train on older dates, test on the most recent period.
5. Which is unsupervised: churn yes/no, house price, customer segments?Customer segments: there is no target column.
6. Why drop customerID?It is a random name tag with no meaning; the model could memorise it instead of learning patterns.
7. Why is OneHotEncoder(handle_unknown="ignore") important in production?A category never seen in training (e.g. a new payment method) would otherwise crash prediction.
