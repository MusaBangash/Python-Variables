Part 9 · Session 4 (Day 2)

From notebook to product: reproducibility, responsible use and inference

A model in a notebook helps nobody. This part covers what it takes to let other people use a model safely: saving it, predicting on new data, checking inputs, watching for drift, checking fairness, protecting privacy, explaining it honestly, and documenting it in a model card. Part B is Practical 6, which does all of it, ending with a Streamlit app. Open Practical 6 in Colab.

Part A · The concepts

9.1 Reproducibility: can someone get the same result again?

A good recipe lists exact ingredients, amounts and oven temperature, so anyone can bake the same cake. "Some flour, bake until done" can't be repeated. An ML experiment needs the same: exact data, code, settings and random seeds.

Practice How
Fix random seeds random_state=42 in splits, models, CV folds
Record each experiment date, data version, features, model, settings, CV and test scores (a CSV or a tool like MLflow)
Version the code Git: every result points to a commit
Record library versions requirements.txt; a model saved with one scikit-learn version may not load in another
Keep the data version the exact file (or a date / hash) used for training
One pipeline the same preprocessing for training and prediction

9.2 Saving and loading model artifacts

import joblib
joblib.dump(pipeline, 'model.joblib')     # save the WHOLE pipeline, not just the model step
pipeline = joblib.load('model.joblib')    # in another program, another day

Save next to the model: the input schema (columns, types, allowed values), the threshold, and a record of how it was made (Practical 6 saves schema.json and model_info.json).

Never load a .joblib / pickle file from someone you don't trust: loading can run hidden code. And load with the same library versions that saved it.

9.3 Inference: using the model

Inference = making predictions with a trained model.

Type How Example
Batch run on a whole file on a schedule Monday morning call list of risky customers
Real-time (online) one request at a time, answer in milliseconds, usually through an API loan check while the customer waits
Interactive app a person fills a form Streamlit page for the sales team

9.4 Input schema and validation

Models never complain: they will happily predict for tenure = −5, a column with a typo, or a contract type that doesn't exist. Validate before predicting:

Check If it fails
all expected columns present reject (error)
numbers are numbers reject
values inside the training range predict, but warn (the model is guessing outside its experience)
categories seen in training predict (one-hot "ignore"), but warn
missing values impute, but log how often

9.5 Drift: models age

Kind What changes Example How to detect
Data drift the inputs many more new customers after a marketing campaign compare input or score distributions (PSI) with training
Concept drift the relationship between inputs and the answer a competitor's offer makes long-time customers leave too performance drops when real outcomes arrive
Performance drift the measured quality recall falls from 0.81 to 0.65 track metrics on new labelled data

PSI (population stability index): < 0.1 stable · 0.1–0.25 watch · > 0.25 investigate. When alarms ring: investigate, collect fresh labelled data, retrain with the same pipeline, re-test, update the model card.

9.6 Bias, fairness and representativeness

A model learns the patterns in its data, including unfair ones.

Source of bias Example
Unrepresentative data a face-recognition model trained mostly on light-skinned faces works worse on darker skin
Historical bias a hiring model trained on past hires copies past discrimination
Proxy features removing "gender" doesn't help if "first name" or "job title" still encodes it
Label bias "who was arrested" is not the same as "who committed a crime"

What to do: 1. Measure per group: compute the same metric (recall, precision, error) for each group of a sensitive attribute (sex, age group, region…). Practical 6 does this. 2. Explain gaps in the model card; decide with the business whether they are acceptable. 3. Consider removing sensitive features if they add nothing, but remember proxies. 4. Keep a human in the loop for high-stakes decisions.

Equal accuracy is not the only kind of fairness, and different fairness definitions can't all be satisfied at once. Write down which one matters for your use case and why.

9.7 Privacy and sensitive data

Principle In practice
Collect the minimum don't keep names or phone numbers in training data if the model doesn't need them
Remove direct identifiers drop IDs, names, emails; keep a separate protected lookup if needed
Protect access who can read the data and the model's outputs?
Purpose limitation data collected for billing shouldn't silently be reused for something else
Retention delete data you no longer need
Legal duties many countries have data-protection laws (e.g. GDPR in Europe); follow your organisation's rules
Special care health, finances, religion, ethnicity, children: extra protection, often extra legal rules

9.8 Explainability and the limits of feature importance

Tool Explains Limits
Coefficients (linear/logistic) direction and size of each feature's effect only for linear models; correlated features share credit unpredictably
Impurity importance (trees) which features the trees used biased towards many-valued features (a random column was ranked #2)
Permutation importance how much the score drops if a feature is scrambled correlated features hide each other
SHAP values each feature's contribution to one prediction slower; still associations, not causes

None of these prove causes. "Fiber customers leave more" might mean fiber is overpriced, or fiber areas have more competitors. To prove a cause you need an experiment (e.g. give a discount to a random half).

9.9 Model cards

A model card is a short document that travels with the model:

Section Answers
Intended use what it's for, who uses it, and what it must not be used for
Data where the data came from, how it was cleaned, what period it covers
Model type, key settings, threshold and why
Evaluation metrics on the test set, compared with the baseline
Fairness metrics per group and any gaps
Limitations where it fails or hasn't been tested
Risks & responsible use privacy, misuse, monitoring plan
Reproducibility seed, versions, date, code commit

Practical 6 writes one automatically from the real numbers.

9.10 When a model is NOT the right solution

  • A simple rule is nearly as good (Session 1: one rule caught 88% of leavers).
  • There are no reliable labels, or the past won't repeat.
  • Decisions are high-stakes and must be fully explained to each person, and no human checks them.
  • False positives harm people (e.g. wrongly accusing someone of fraud) and you can't afford them.
  • The cost of building, monitoring and maintaining is bigger than the benefit.

Then: use a rule, keep a human in the loop, collect better data first, or don't build it.

Practical 6 · From notebook to product (churn)

Goal: turn a trained model into something other people can use safely:

  • churn_model.joblib: the whole pipeline (preprocessing + model)
  • schema.json: which columns the model expects, their types and allowed values/ranges
  • model_info.json: how it was made (data, seed, threshold, scores, library version), so anyone can reproduce or audit it

3 · Check inputs before predicting (input schema validation)

Models don't complain about nonsense; they happily predict for a customer with tenure −5 or contract "banana". We must check first:

  • errors (don't predict): missing columns, text in a number column
  • warnings (predict, but a human should look): values outside the training range, unseen categories, missing values
def validate(df, schema):
    errors, warnings = [], []
    for col, spec in schema.items():
        if col not in df.columns:
            errors.append(f'missing column: {col}'); continue
        if spec['type'] == 'numeric':
            values = pd.to_numeric(df[col], errors='coerce')
            if (values.isna() & df[col].notna()).any():
                errors.append(f'{col}: contains non-numbers')
            outside = (values < spec['min']) | (values > spec['max'])
            if outside.any():
                warnings.append(f"{col}: {int(outside.sum())} value(s) outside training range {spec['min']}–{spec['max']}")
        else:
            unseen = set(df[col].dropna().astype(str)) - set(spec['values'])
            if unseen:
                warnings.append(f'{col}: unseen categories {sorted(unseen)}')
    return errors, warnings

bad = batch.drop(columns=['churn_probability', 'call']).head(3).copy()
bad.loc[bad.index[0], 'tenure'] = -5
bad.loc[bad.index[1], 'Contract'] = 'Three year'
bad = bad.drop(columns=['PaymentMethod'])
errors, warnings = validate(bad, schema)
print('ERRORS  :', errors)
print('WARNINGS:', warnings)

ERRORS  : ['missing column: PaymentMethod']
WARNINGS: ['tenure: 1 value(s) outside training range 0.0–72.0', "Contract: unseen categories ['Three year']"]

Because of the error (a missing column), this file must be rejected, not predicted. The warnings would be logged for a person to review. In production this check runs before every prediction.

4 · Fairness: does the model work equally well for different groups?

The same metric, per group. Big gaps need an explanation in the model card. We check gender and SeniorCitizen on the test set.

test = X_test.assign(actual=y_test.values, flagged=(test_proba >= THRESHOLD).astype(int))
rows = []
for col in ['gender', 'SeniorCitizen']:
    for value, g in test.groupby(col):
        rows.append({'column': col, 'group': value, 'customers': len(g), 'actual churn rate': g['actual'].mean(),
                     'flagged rate': g['flagged'].mean(), 'recall': recall_score(g['actual'], g['flagged']),
                     'precision': precision_score(g['actual'], g['flagged'])})
fairness = pd.DataFrame(rows).round(3)
fairness
column group customers actual churn rate flagged rate recall precision
0 gender Female 687 0.281 0.431 0.793 0.517
1 gender Male 722 0.251 0.434 0.829 0.479
2 SeniorCitizen 0 1187 0.233 0.382 0.764 0.465
3 SeniorCitizen 1 222 0.441 0.698 0.939 0.594

Reading it:

  • Gender: men and women get similar recall (0.83 vs 0.79) and precision. No big gap.
  • Senior citizens: flagged far more often (70% vs 38%), but they also actually leave far more often (44% vs 23%). The model catches 94% of senior leavers but only 76% of non-senior leavers: non-senior leavers are missed more often.

This is not automatically "unfair", but it is a real difference in quality between groups, and it must be written in the model card. The business should decide: is it acceptable that seniors get far more retention calls (the offer must be helpful, not pushy), and do we need a lower threshold for non-seniors to catch more of them?

Should we just delete gender from the features? Removing a sensitive column doesn't guarantee fairness (other columns can act as proxies), but if it adds nothing to accuracy, removing it is a sensible, simple choice. (Exercise 1.)

5 · Drift: is new data like the training data?

Models quietly get worse when the world changes. A standard check is the Population Stability Index (PSI) on the model's scores: below 0.1 stable, 0.1–0.25 watch, above 0.25 investigate.

def psi(expected, actual, bins=10):
    edges = np.quantile(expected, np.linspace(0, 1, bins + 1)); edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected) + 1e-6
    a = np.histogram(actual, edges)[0] / len(actual) + 1e-6
    return float(np.sum((a - e) * np.log(a / e)))

train_scores = model.predict_proba(X_train)[:, 1]
print(f'PSI, this month (test set) vs training: {psi(train_scores, test_proba):.3f}')

future = X_test.copy()                                # simulate: a marketing push brings many brand-new customers
idx = future.sample(frac=0.5, random_state=1).index
future.loc[idx, 'tenure'] = 1
future.loc[idx, 'TotalCharges'] = future.loc[idx, 'MonthlyCharges']
future.loc[idx, 'Contract'] = 'Month-to-month'
print(f'PSI after a wave of new customers:      {psi(train_scores, model.predict_proba(future)[:, 1]):.3f}')

PSI, this month (test set) vs training: 0.014
PSI after a wave of new customers:      0.228

This month is stable (PSI ≈ 0.01). The simulated wave of new customers raises PSI to about 0.23: the "watch" zone, close to the 0.25 alarm. A team would start investigating now.

  • Data drift: the inputs change (above).
  • Performance drift: when real outcomes arrive weeks later, compare actual recall/precision with the model card's numbers. When either alarm rings: investigate, collect fresh labelled data, retrain with the same pipeline, test, and update the model card.

7 · A Streamlit app

Streamlit turns a Python script into a web page. The app below loads the saved model, shows a form, validates the input, and shows the churn probability and decision. %%writefile saves the cell as a file.

%%writefile app.py
import json
import joblib
import pandas as pd
import streamlit as st

st.set_page_config(page_title='Churn risk')
model = joblib.load('churn_model.joblib')
schema = json.load(open('schema.json'))
info = json.load(open('model_info.json'))

st.title('Customer churn risk')
st.caption(f"Logistic regression · test ROC AUC {info['test_roc_auc']} · threshold {info['threshold']}")

values = {}
for col, spec in schema.items():
    if spec['type'] == 'numeric':
        values[col] = st.number_input(col, min_value=spec['min'], max_value=spec['max'], value=spec['min'])
    else:
        values[col] = st.selectbox(col, spec['values'])

if st.button('Predict'):
    row = pd.DataFrame([values])
    p = float(model.predict_proba(row)[:, 1][0])
    st.metric('Probability of leaving', f'{p:.0%}')
    if p >= info['threshold']:
        st.error('High risk: add to the call list')
    else:
        st.success('Low risk')

with st.expander('Model card'):
    st.markdown(open('MODEL_CARD.md').read())
